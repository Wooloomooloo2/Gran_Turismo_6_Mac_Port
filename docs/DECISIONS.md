# Decisions

Numbered, dated, with reasoning. Do not re-litigate the owner decisions (D1-D12 and D15) without the owner.

## Owner decisions (2026-10-27)

**D1.** Native translation, not emulation. Don't re-litigate.

**D2.** Priorities: locked 60 → MetalFX 4K → wheel. Controller first.

**D3.** Target game version **1.22** (final), European edition **BCES-01977**.

**D4.** Updates are fetched from Sony's update server with proper certificate verification, using Sony's root certificates taken from the firmware on the player's own disc.

**D5.** Online play out of scope.

**D6.** First milestone: the first menu.

**D7.** Public repo from the start, releases and outside contributors welcome, like Bloodborne.

**D8.** Reuse Bloodborne's launcher, MetalFX work and conventions where they fit.

**D9.** **A runtime fallback is allowed** for code not found ahead of time (SPU jobs loaded from data, overlays, missed indirect branches). It logs every use so the code can be translated ahead of time next run. Release builds aim for zero fallback use in normal play. This doesn't break O1: the product is still a translated native program.

**D10.** **Handling must match the PS3 exactly.** Physics and any gameplay-affecting SPU or PPU work is a faithful translation (exact SPU float and VMX behaviour), checked by determinism tests against reference traces recorded from RPCS3. Hand-written native replacements are allowed only where the player can't feel the difference (for example audio mixing, graphics setup), and each one is recorded in DECISIONS.

**D11.** **If a Mac can't hold 60:** first lower the internal resolution automatically and upscale with MetalFX. Beyond that, best effort on frame rate. Below-60 on a base M1 is not a project failure.

**D12.** **The app includes its own compiler** (a pinned LLVM/clang), so players don't install Apple's developer tools. During development, use the toolchain already on this Mac. **Large uploads from the owner's connection should happen late:** keep early releases small, and prefer ways that avoid uploading the toolchain from here (for example the app fetching a pinned, checksummed official LLVM build on first setup, or CI building release bundles). The builder picks the mechanism and records it in DECISIONS.

## Builder decisions

**D13 (2026-10-27).** C++ `gt6unpack` adapted from RPCS3 crypto; Python only for dev-time mapping. Reason: the unpacker ships to players and must not depend on RPCS3 or a Python install; RPCS3's crypto is GPL-2.0 and credited.

**D14 (2026-10-27).** Updates are installed as a separate `dev_hdd0` tree, as on a real PS3, not merged into the disc tree. Reason: matches how the game expects to find them, keeps the disc image untouched, and makes verification per layer.

**D15 (2026-10-27, owner).** Public PS3 decryption keys live in source, following the RPCS3 and ps3recomp precedent. Reason: players need no key hunting; the keys are publicly documented. This is a legal-exposure call and was made by the owner. No console-unique or disc-specific keys are ever committed (`keys.local*` is git-ignored).

**D16 (2026-10-27).** SELF decryption checks the section hash of every program segment and skips the hash of the section header table and SCE version sections. Reason: on the real disc executables the segment hashes match exactly, but the other two never match under any coverage tried (evidence in FINDINGS). Checking them would reject valid files. The decrypted ELFs are byte-identical to RPCS3's.

**D17 (2026-10-27).** The SELF decrypter supports retail ELF64 application and free-licence NPDRM SELFs only. Debug/fake SELFs, ELF32 SELFs and paid NPDRM licences raise clear errors. Reason: GT6's executables and its update packages need nothing more; less code to get wrong.

**D18 (2026-10-27).** The built disc layer (`dev_bdvd`) holds `PS3_DISC.SFB` and `PS3_GAME` only. The disc's `PS3_UPDATE` (system firmware) is left out, and the copied tree is made owner-writable. Reason: the game never reads the firmware, firmware must stay out of the project's outputs, and a read-only tree from a mounted image could not be rebuilt or removed.

**D19 (2026-10-27).** The klicensee that opens the update `EMAIN.SELF` files is found at build time in the player's own decrypted update `EBOOT.BIN`, never stored in the repository. A candidate key is accepted only if it decrypts the file with every program-segment hash matching. Reason: the game ships the key in its own executable as a config default (evidence in FINDINGS), so finding it there is reproducible from the player's files. Committing it would be a title-specific key, against D15. The key was captured once from RPCS3 to confirm the finding. That copy has been deleted, and the build neither needs nor reads a key file.

**D20 (2026-10-27).** The manifest covers `dev_bdvd`, `dev_hdd0` and `decrypted`, and nothing else. `build.json` is left out of the manifest and out of the EXTRA check. Reason: it holds timings and local paths that change on every run, so including it would make every build fail verification. Decided by the implementer.

**D21 (2026-10-27).** The code map covers the two executables a v1.22 console runs: the update `EBOOT.BIN` and the `USRDIR/EMAIN.SELF` it launches. The other 19 decrypted executables get a size and SHA-256 row only. Reason: the 1.22 `EBOOT.BIN` always launches `USRDIR/EMAIN.SELF` (evidence in FINDINGS); the disc, `FIXEDELF114` and `TPPS-01.xx` copies are older or standby builds that never run on 1.22. `scripts/map_game.py --elf` maps any of them if needed. Ruled by the controller; launch target confirmed by the implementer.

**D22 (2026-10-27).** `map_game.py` runs each ps3recomp tool as `python -I -c <runner> <tool> ...`, where the runner adds only that tool's own folder to the import path. Reason: under `python -I` the script's folder is not on the import path, and `extract_spu_images.py` fails with `ModuleNotFoundError: No module named 'spu_elf'` (the other tools add their folder themselves). The runner keeps isolated mode (no environment variables, no current-folder imports) without patching ps3recomp. Decided by the implementer.

**D23 (2026-10-27).** `map_game.py` also scans each ELF for job modules stored raw, using the header ps3recomp's `extract_jobmods.py` defines (and its file naming), and writes them next to its output. Reason: `extract_jobmods.py` only looks inside `patch.sdat`/`data.sdat` archives, which GT6 does not have, so it finds none, while `EMAIN.SELF` carries 57 job modules in its own code segment. Without the scan the map would report no job modules. Decided by the implementer.

**D24 (2026-10-27, ruling R5).** The files adapted from RPCS3 (`keys`, `self`, `pkg` in `tools/gt6unpack/src/`) are GPL-2.0-only, and `gt6unpack` as a whole is distributed under GPL-2.0-only. Everything else in the repository stays GPL-2.0-or-later. Every source file carries an `SPDX-License-Identifier` line saying which. Reason: RPCS3 states "Most files are licensed under the terms of GNU GPL-2.0-only", and its `rpcs3/Crypto` files carry no different notice, so code adapted from them cannot be offered under "or later" terms; the unpacker links that code, so the whole tool takes the stricter licence. Ruled by the controller after the final milestone 1 review.

**D25 (2026-10-27).** The lift's code end is the end of the last executable ELF section, read from the section headers. Reason: without it 3.7 GB of read-only data and embedded SPU programs are lifted as code (FINDINGS, "Translating EMAIN"). Decided by the implementer.

**D26 (2026-10-27).** Generated code, objects, binaries and run outputs live in the player's game folder (`<tree>/recomp`, `<tree>/port-build`, `<tree>/runs`), never in the repository. Reason: translated code is a derivative of the game (design spec, section 3). The translate tool refuses an output path inside a git work tree, and replaces an existing output folder only if it holds a `translate.json` it wrote, never the tree or a folder containing it (its `.staging` and `.old` folders too, only when they carry its marker or `translate.json`). The port's configure refuses a `GT6_TREE` or build folder inside any git work tree, by real path as well, and `eboot_effects.py snapshot` refuses such an output. Decided by the implementer; the output-folder and any-work-tree checks added after the milestone 2 final review.

**D27 (2026-10-27).** SPURS and SPU work run on ps3recomp's HLE SPURS with the lifted SPU code, and its SPU interpreter as the logged fallback. No firmware LLE: no Sony module (liblv2, libsre, any PRX from dev_flash) is loaded or required. Configure stops with an error if the translate output holds `taskset_policy_bytes.c` (libsre's policy module bytes, which ps3recomp's tools can write) rather than compile it (controller ruling, milestone 2 final review). The translate step lifts with `--allow-partial`, so an SPU program or job module that lifts only partly does not block the build; it is listed in `translate.json` and FINDINGS and runs in the interpreter (D9). Reason: design spec 6.3 (the shipped default must work without Sony modules), and O9. Decided by the implementer, per the milestone 2 plan.

**D28 (2026-10-27).** ps3recomp changes are carried as patch files in `patches/ps3recomp/`, applied in filename order to the submodule's working tree by `scripts/apply_ps3recomp_patches.sh` (which skips a patch already applied), each written so it can go upstream and headed with its upstream status. `scripts/translate_game.py` applies them to the ps3recomp it lifts with before running any tool, then checks with `--verify` that every patch is in, and refuses otherwise; only then does it record the patches' hash in `translate.json`. Configure applies them again before comparing that hash, and refuses a tree translated under a different patch set. The submodule pointer stays at the pinned commit; only its working tree carries the patches (undo: `git -C third_party/ps3recomp checkout . && git -C third_party/ps3recomp clean -fd`, since the patches also add files). Translate applying them was added after the milestone 2 final review: before it, a fresh clone failed to translate, and a later lifter patch would have let a stale lift be recorded under the new hash. Reason: the pinned submodule stays a clean upstream commit, every change can be reviewed, and nothing needs a fork pushed before the owner agrees. Decided by the implementer, per the milestone 2 plan.

**D29 (2026-10-27).** During development the port builds with the tools on this Mac: Apple clang, CMake and Ninja, and Homebrew's sdl2 (now `sdl2-compat` over SDL3), glslang and spirv-cross. Bundling them for players follows D12 (O12) later (BACKLOG, Mac GUI). Reason: D12 allows the local toolchain during development, and the runtime needs SDL2 for pad and audio and glslang plus spirv-cross to turn guest shaders into Metal ones. Decided by the implementer, per the milestone 2 plan.

**D30 (2026-10-27).** Lifted PPU code is compiled at `-O1` in every build type (72 s for the 65 chunks on the M4 Max, FINDINGS); lifted SPU code at `-O2`; the runtime takes the build type's level. The level is revisited in milestone 5 (locked 60) with measurements. Reason: the chunks are up to 5 MB of generated C++ each, and higher levels cost far more compile time and memory for a gain nobody has measured yet; `-O1` already inlines the small helpers the lifted code is made of. This follows ps3recomp's template. Decided by the implementer, per the milestone 2 plan.

**D31 (2026-10-27).** The port starts `EMAIN.SELF` directly with the launch contract in FINDINGS ("What the 1.22 EBOOT leaves on disk, and how EMAIN is launched"): the process `/dev_hdd0/game/BCES01977/USRDIR/EMAIN.SELF`, argc 2 with `argv[0]` and `argv[1]` both that path, an empty environment and no data block, as the 1.22 `EBOOT.BIN` spawns it (`sceNpDrmProcessExitSpawn2`, measured under RPCS3). `port/main.cpp` passes it through ps3recomp's `PS3_BOOT_PATH` and `PS3_ARGV`, from which `ppu_run` builds the entry's argc, argv and envp. It runs on a play folder made by `scripts/prepare_play.py`, which carries the EBOOT's on-disk effects; the verified tree is never run (D32). The 1.22 `EBOOT.BIN` is not translated. Reason: the EBOOT only checks two files exist, rewrites 6 files that EMAIN's first-run install reads (without them EMAIN skips the 1.07 data patch), and spawns. The script reproduces those 6 files byte-identically, with the rule decoded from 0x1143c. So translating the EBOOT would add a second program and a cross-process klicensee hand-off for nothing. Ruled by the controller; measured and decoded by the implementer.

**D32 (2026-10-27).** The game runs on `<tree>/play/dev_hdd0`, an APFS clone of the verified `<tree>/dev_hdd0` made by `scripts/prepare_play.py` with the 1.22 EBOOT's on-disk effects applied. `<tree>/play/prepare.json` records what was applied, the source `build.json` (SHA-256, tool version, title, version) and the time. The port's `/dev_hdd0` defaults there (`PS3_HDD0_ROOT` still overrides), and it refuses to start unless that folder exists with `prepare.json` beside it (for an override, `$PS3_HDD0_ROOT/../prepare.json`). The script builds the folder in a staging folder and renames it into place only after writing `prepare.json`, and `--force` replaces only a folder holding this tool's `prepare.json`, never the tree or a folder containing it. An existing play folder is kept unless `--force` is given, because a first run has changed it. `scripts/boot_game.py` records each boot in `prepare.json` (`"booted"`: the run) and warns, without refusing, when it boots a play folder an earlier run used, pointing at `prepare_play.py --force` (controller ruling, milestone 2 final review). `gt6unpack` and the manifest are unchanged. Reason: EMAIN's first run moves thousands of files between `TPPS-*` and `PDIPFS`. Running on the verified tree would break `gt6unpack verify` and lose the known-good copy, while a clone costs 2.6 s and no disk space until files change. Ruled by the controller.

**D33 (2026-10-27, controller ruling A).** SPU images GT6 runs that the translate step did not find (SPURS job binaries and the `Wws_Job` policy module) run in ps3recomp's SPU interpreter, the D9 fallback, never dropped; and the job-chain walker sends no made-up completion events. The port sets `SPU_JOB_INTERP=1` and `SPURS_JOB_SYNTH_EVENTS=0` (patch 0008, `port/gt6_spurs.cpp`); every interpreted run is counted in the milestone log (`spu:interp:<fingerprint>`, `report.json` `spu_interpreted`). Each image is dumped once to `<tree>/spu-missed/` (`SPU_DUMP_MISS`: `spujob_` linked for LS 0, `spupm_` for LS 0xA00), and `scripts/translate_game.py` lifts what it finds there on its next run and registers it by fingerprint (`spu_missed_register.c`; counts in `translate.json` `spu.missed`), so the next build runs it as native code. Reason: a dropped job's work never happens and a faked completion corrupts game state (O10); on hardware the job manager sends no completion event, the job reports its own end. The images are in EMAIN itself (FINDINGS), so a static finder can replace the dump later (BACKLOG).

**D34 (2026-10-27).** A guest `longjmp` unwinds the lifted host frames with a host `_longjmp` (patch 0009). Every direct call to the title's C library `setjmp` is bracketed by a host `_setjmp` into a frame held by the calling lifted function (dropped on each of its returns); the lifted `longjmp`, after restoring the guest registers, jumps to the newest frame for that `jmp_buf` and restores the runtime's indirect-call depth. `scripts/translate_game.py` finds `setjmp` and `longjmp` in EMAIN by their first six instructions (one match each; recorded in `translate.json` `sjlj`) and passes them as `--setjmp`/`--longjmp`. Reason: lifted, every guest call is a host call, so a guest longjmp only returned from itself; GT6's file worker aborts a decode that way, and the decoder then overran into other state (FINDINGS, bring-up round 8). The alternatives were a hand-written override of GT6's decoder (a D10 replacement, covering one of the 22 setjmp call sites) or running the guest on its own stack (a different execution model). Limits: no lifted C local may change between the setjmp and the longjmp (true of the lifter's output today), and a jump over a host HLE frame skips its destructors and locks (ppu_sjlj.h).

**D35 (2026-10-27).** Long boot runs keep a capped series of numbered frames and per-frame draw statistics (patch 0010, `scripts/boot_game.py`). The runtime (draw-engine path, the Metal backend's default) numbers presents from 1; with `PS3RECOMP_METAL_FRAME_DIR` it dumps present 1 and every `PS3RECOMP_METAL_FRAME_EVERY`-th (default 60) as `frame_<presented, 6 digits>.ppm`, at most `PS3RECOMP_METAL_FRAME_MAX` (default 300), each written to a hidden temporary name and renamed into place; with `PS3RECOMP_DRAW_STATS` it writes one `<presented> <draw calls> <clears>` line per present, flushed per line because runs end with the process killed. A draw call is one BEGIN_END group holding at least one draw command, counted whether or not the engine could draw it; a clear is one CLEAR_SURFACE, whatever its mask. The engine counts them and latches them before the backend's present, and it presents once per guest flip, so they are the counts since the last flip. A present with no surface to show does not reset the counts, so its draws and clears carry into the next present. The policy and writers are a plain-C header (`libs/video/rsx_frame_series.h`) so they test without a GPU; the single-file `PS3RECOMP_METAL_FRAME_DUMP` is unchanged, but the harness no longer sets it (the series replaces it, and frame 1 is now always kept). The legacy vtable render path is not covered (BACKLOG). Disk caps: the harness stops the dumps by creating `frames/STOP`, which the runtime checks before each dump (one `stat` per due dump), rather than moving the folder aside, so every dump stays where `report.json` names it and the game runs on untouched; it does so before launch and on every 0.2 s poll once `frames/` exceeds `frame_bytes` (2 GB) or free space falls below 20 GB, and records `dump_stopped` `bytes` or `disk` (`max` when the frame cap was reached). A frame counts as drawn when its present had at least one draw call and more than 1% of its pixels are not black (`nonzero_share`, any non-zero channel). `--until time` runs to `--seconds`, a flip does not stop it, hang detection still applies only before the first flip, and a run that reaches the limit without crashing is `timeout` with its frames kept, while one that ends by itself before then is `exited` (a crash is still `crashed`); the CLI exits 0 for that when the game flipped and at least one frame was kept. `--png` converts with macOS `sips`; `--prune` deletes all but the newest 10 folders named like a run (`yyyymmdd-HHMMSS`) and nothing else in `runs/`. Reason: milestone 2's single overwritten dump could not show how the screen changes during GT6's minutes-long first-run install, nor tell a cleared frame from an undrawn one; the caps keep a 4-minute run at about 1.3 GB on a disk with 69 GB free. Writing the stop file never fails a run: an error is printed and the run carries on to its report, and `--prune` warns and carries on if a folder cannot be deleted (fix round 1). Decided by the implementer, per the milestone 3 plan.

**D36 (2026-10-28).** The SDK's PPU fiber contexts (`cellFiberPpuContext*`: AttributeInitialize, Initialize, Finalize, Run, Switch, ReturnToThread, Self, CheckStackLimit) run on a host thread each, with a baton (patch 0011, `libs/spurs/cellFiber.c`). Initialize creates the context's host thread (256 MB reserved stack, as for PPU threads); one lock and a condition variable per context and per Run let exactly one context, or the thread blocked in `cellFiberPpuContextRun`, execute at a time. **Guest identity:** a context runs on the PPU thread that resumed it, as on the console, so every Run or Switch gives it that thread's `thread_id` and r13; `sys_ppu_thread_get_id`, lwmutex ownership and `__thread` data inside a context are the running thread's. **setjmp/longjmp (D34):** every host thread-local of the runtime is per context, including `g_sjlj_top`, which starts empty on a context's thread, so a guest longjmp can only land on a setjmp made on its own context (one aimed at another context finds no frame and returns, the pre-D34 behaviour); context threads are never reused, so the interrupt-handler re-entry gap (BACKLOG) does not reach them. **Finalize** on a suspended context sets a kill flag; its thread longjmps from the suspending call to its base frame (skipping lifted frames and one HLE dispatch frame, which hold no lock) and exits, and Finalize joins it. The host record is kept for the next Initialize, because each context's `ppu_context` joins the runtime's reservation set, which has no removal. Process exit does not wait for suspended contexts. **Errors** follow RPCS3's argument checks (NULL_POINTER, ALIGN; the calls are stubs there) and the SDK's meanings: PERM for Run from a context and for Switch/ReturnToThread/CheckStackLimit from a thread, INVAL for an address with no context, STAT for a running or ended context, a Switch to itself and a second Initialize. Where neither documents it, an entry that returns ends the context and Run returns cause 0, and a guest stack under 1 KB is INVAL. Reason: a suspended lifted context includes host frames, so a switch must suspend a host call chain. A thread per context keeps all thread-local runtime state per context with no list to swap (ucontext, used by ps3recomp's scheduler API, would share `g_sjlj_top`, the indirect-call depth, the trampoline and the callback stack slot between contexts), and GT6 has one context and calls Run at most about once a frame (1k-9k calls in 40 s while the call was faked, FINDINGS), so the handoff cost (about 5 µs a round trip) does not matter. Hand-written arm64 switching would be faster but needs the same thread-local swapping. Decided by the implementer, per the milestone 3 plan.

**D37 (2026-10-28).** Where the menu-path handlers of patches 0013-0017 depart from RPCS3 or the PS3, the departures are these, and each patch text names its own. Everything not listed follows RPCS3's behaviour and codes. Each is either a guard where RPCS3 would read through a bad pointer or divide by zero (so the console would fault, and an answer is safer than a host crash), or a deliberate "not available" answer, since this Mac has no such device or library (D10, O10).
- **SPURS (0013).** The runtime has 16 workload slots, so a CellSpurs2's workloads 16-31 cannot be added. `cellSpursDestroyTaskset2` checks for NULL (NULL_POINTER) and 128-byte alignment (ALIGN), then destroys as `cellSpursDestroyTaskset` does. RPCS3 leaves it unimplemented (CELL_OK, no checks), so these checks follow the other taskset calls by analogy. Brought in line with RPCS3 in this fix: AddWorkload drops a stale receiver naming the slot it fills; RemoveWorkload lets the receiver go and resets the flag; `cellSpursInitializeWithAttribute2` refuses attribute revisions above 2 and checks in RPCS3's order (attribute NULL, attribute alignment, revision, spurs NULL, spurs alignment).
- **cellUsbd (0014).** The extra-LDD calls now follow RPCS3's lv2 `sys_usbd_register_extra_ldd` and `sys_usbd_unregister_extra_ldd`: EINVAL before init, EEXIST, ESRCH, no limit, no range check. RPCS3's HLE libusbd calls are CELL_OK stubs. A NULL driver answers EINVAL (a guard). *Not available:* no USB device is ever attached, so no driver is probed.
- **sys_mempool (0015).** free_block follows RPCS3 and refuses only a block past the chunk's end. Guards: a NULL id pointer and a zero block size are EINVAL, and running out of the 1023 ids is EAGAIN. A pool is reference counted, so a destroyed pool's record and mutex are freed once no call is inside it.
- **sys_prx_get_module_list (0015).** *Not available:* the list is empty, because no PRX is ever loaded (every library is HLE, D27).
- **cellMusic (0016).**
  - `cellMusicSetVolume2` ignores its level, which arrives in f1 and is not read by the generic handler. RPCS3 keeps the level, but nothing plays here.
  - `cellMusicFinalize2` clears the callback, while RPCS3 keeps it. Calls after Finalize2 then answer GENERIC, as they do before Initialize2.
  - *Not available:* `cellMusicSelectContents2` answers CANCELED at once, as if the user closed an empty list, because there is no music library. RPCS3 opens its own media dialog.
- **sceNpTrophy (0017).** `sceNpTrophySetSoundLevel` follows RPCS3 (INVALID_ARGUMENT, UNKNOWN_CONTEXT, UNKNOWN_HANDLE). The module's error values were not the SDK's. Every name with an SDK code now has the SDK's 0x800229xx value. Five names with no SDK code keep the module's own values (BACKLOG).

Reason: the Task 4 review found several patch texts claiming "follows RPCS3" where the code did not, so the record needs to say exactly where the port's answers differ. Departures that could simply be removed were removed (the receiver lifecycle, the attribute-revision check, the usbd codes, the mempool free test, the trophy codes). Decided by the implementer, per the Task 4 review.

**D38 (2026-10-28).** `sys_mmapper_allocate_address` places a reservation whose size is a power of two larger than its alignment on its own size (natural alignment). It falls back to the requested alignment only when no such span is left (patch 0018). Reason: lv2 hands out address space first-fit from the bottom of user space, so GT6's early reservations land on large boundaries there. Under RPCS3, 256 MB goes to 0x30000000 and 512 MB to 0x40000000. ps3recomp keeps its own windows at 0x50000000-0x6FFFFFFF and put GT6's 512 MB heap at 0x70000000, across 0x80000000. GT6's heap numbers its 8 KB pages as `(address >> 13) & 0xFFFF`, so its page numbers wrapped there. Every realloc on that heap then failed, and the C library's atexit, on that failure, returned holding its lock. That leaked lock was the fiber deadlock (FINDINGS, bring-up round 1). The alternative, reproducing lv2's exact layout, would mean moving the runtime's own windows (the HLE heap, audio and sys_vm), a much larger change with every title as a risk. Natural alignment is always a valid placement under lv2's alignment rules. Decided by the implementer.

**D39 (2026-10-28).** `/dev_hdd1`, the cache partition, is `<tree>/play/dev_hdd1`, beside the play folder's `dev_hdd0`. `port/main.cpp` makes it when missing and gives it to both file layers: `PS3_HDD1_ROOT` for `ppu_fs.cpp` and `sys_fs.c`, and a `cellFs.c` path mapping. `$PS3_HDD1_ROOT` overrides. `prepare_play.py --force` replaces the whole play folder, so a fresh play folder starts with an empty cache, as a console does before a title's first cache mount. Reason: GT6's first-run install decodes each patched file into `/dev_hdd1/cache/BCES01977/...` (`.plain`), then renames it. With no root set, `ppu_fs.cpp` resolved `/dev_hdd1` into the disc layer (`<tree>/dev_bdvd/cache`, inside the verified tree), while `cellFs.c` had no `/dev_hdd1` mapping at all. Its rename answered ENOENT, and GT6 stopped the install with a warning dialog (FINDINGS, bring-up round 2). A port setting, not a ps3recomp patch: where a title's partitions live is the port's choice, as for `/dev_hdd0` (D32). Decided by the implementer.

**D40 (2026-10-28).** Unattended runs press pad buttons with `boot_game.py --press SECONDS:BUTTON` (repeatable). The harness turns the presses into ps3recomp's existing `PAD_SCRIPT` (`<seconds>:<CELL_PAD_CTRL mask>,...`, in `libs/input/cellPad.c`), and records them in `report.json` `presses` and in `summary.md`. In cellPad a press fires on the first poll at or after its time and is held for 40 polls. The clock starts at the game's first `cellPadGetData`, not at launch (about 2 s later for GT6). Reason: GT6's "Installation complete." dialog waits for Cross (FINDINGS, RPCS3 reference), so a run past the install needs a scripted press. The plan expected a new generic patch (`PS3RECOMP_PAD_SCRIPT`), but the pinned ps3recomp already carries this env-driven script on the real pad path (a fresh report, both digital halves), so no patch is needed. Decided by the implementer.
